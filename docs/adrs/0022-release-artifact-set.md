# ADR-0022: Release Artifact Set

## Context

Each tagged release publishes machine-readable artifacts at a stable URL so agents and integrators can pin to the protocol surface without checking out the repository.

The native proto surface is owned by `zinder-proto`:

- Generated Rust types are baked into the workspace at build time.
- The vendored lightwalletd protocol is published as part of upstream `lightwallet-protocol`; Zinder does not republish it.
- Cross-language consumers need a language-agnostic export of the native protocol surface.

The integration cases the release artifacts cover:

- A Python or Go consumer talks to `WalletQuery` from the OpenAPI artifact or the descriptor set, without vendoring `.proto` files manually.
- An MCP bridge or agent discovers the surface from the same OpenAPI artifact.
- A `grpcurl`-style tool calls methods using the descriptor set without a code-generated stub.

Two artifacts cover every one of those cases.

## Decision

**Two-artifact release set.** Each tagged release publishes:

1. **OpenAPI YAML** — transcoded from the proto surface via `protoc-gen-openapiv2`. Drives ReDoc and Swagger UI for humans, and language-agnostic SDK generators / OpenAPI-to-MCP bridges for agents.
2. **`FileDescriptorSet` binary** — the canonical schema export produced by `buf build`. Drives `grpcurl`, `bloomrpc`, and any other tooling that prefers gRPC-native schemas.

Both artifacts are generated by `buf generate` (driven by `buf.gen.yaml`) and `buf build`, attached to the GitHub Release by `.github/workflows/release-api-docs.yml`, and uploaded as a workflow artifact for review on dry-run dispatches.

**HTML proto docs (`protoc-gen-doc`) are deliberately excluded.** The OpenAPI artifact is the human-readable surface; ReDoc renders it directly. Shipping a static HTML page in parallel would duplicate the content, age separately, and require its own templating story.

**Capability strings are the contract.** Agents pin to capability strings (`wallet.address.transparent_balance_v1`, etc.) advertised by `ServerInfo`. Capability identity is exact-match; a `_v2` capability is a separate string from `_v1`, not a version of it. The `_vN` suffix is part of the identity, never decoded.

**No deprecation surface in v1.** Capability strings can be added, renamed, or removed between releases. A deprecation window lands as a follow-up ADR when a real consumer constraint exists; carrying `deprecated_capabilities` apparatus without that constraint is YAGNI baggage.

**OpenAPI publication URL.** GitHub Releases is the v1 hosting URL. A dedicated documentation domain (`zinder.zfnd.org/api/v1/`) is an operational follow-up that does not change the artifact contract; the workflow attaches both artifacts to the release so the URL is `https://github.com/zcashfoundation/zinder/releases/download/v<version>/...`.

## Consequences

**Agents integrate via OpenAPI.** The OpenAPI artifact is the agent-discovery substrate. OpenAPI-to-MCP bridges (`openapi-mcp`, etc.) materialize an MCP server from the artifact without Zinder writing one. A custom `zinder-mcp` adapter remains a future performance / curation optimization, not a missing primitive.

**Cross-language SDKs are unblocked.** A Python consumer can run `openapi-python-client generate` against the OpenAPI YAML; a Go consumer can run `protoc --go_out=...` against the descriptor set; a TypeScript consumer can use `openapi-typescript`. None of them need to vendor `.proto` files.

**One workflow per release artifact set.** `.github/workflows/release-api-docs.yml` builds both artifacts on every release tag. The workflow runs in the same release pipeline as `release-images.yml` (from Tier B4) so a tag triggers everything at once; consumers fetching artifacts get a coherent set built from the same proto sources.

**No HTML proto docs in v1.** The OpenAPI artifact + ReDoc covers humans; the descriptor set covers tooling. Adding `protoc-gen-doc` later is additive (a third artifact) and reversible if the OpenAPI+ReDoc story turns out to be insufficient.

## Alternatives Considered

**Three-artifact set including `protoc-gen-doc` HTML.** Rejected on YAGNI grounds. The HTML output duplicates the OpenAPI artifact's purpose without consumer-facing benefit. If a human-readable page proves valuable later, it lands as a sibling release artifact without changing the existing two.

**Publish only the descriptor set.** Rejected. Most agent-side tooling expects OpenAPI; cutting OpenAPI to ship one artifact would force every agent integration to use proto-aware tools (`buf curl`, `grpcurl`), which is the wrong default for human-and-agent integration ergonomics.

**Carry a `DeprecatedCapability` apparatus on `ServerInfo`.** Rejected. Deprecation tracking is a contract with users. Reserving fields, attaching `deprecated_at`/`removal_at` date strings, and asserting a 180-day removal window are premature commitments without a real consumer constraint. A deprecation policy ADR can add the proto fields when that constraint exists (proto is additive).

**Date-versioned URLs (`api/v1/2026-05-12/openapi.yaml`)** instead of release-tagged URLs. Rejected. Tag-stamped URLs (`releases/download/v0.2.0/openapi.yaml`) survive a documentation-domain swap; the date is recoverable from the tag's git metadata.
